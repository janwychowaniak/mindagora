# Frontend rules

## Styling (Tailwind 4)

- Utility classes first; `@layer` for base/components/utilities; arbitrary values (`w-[123px]`) for one-offs.
- Dark mode is the only theme in MVP (no toggle); design for it directly.
- Responsive and state variants (`sm:`, `hover:`, `focus-visible:`) where they matter.

## Accessibility

- ARIA landmarks for regions; roles only for custom elements without a semantic equivalent.
- `aria-expanded`/`aria-controls` on expandable UI, `aria-live` for dynamic updates (new messages, errors),
  `aria-label`/`aria-labelledby` for unlabeled controls, `aria-current` for the active item.
- Do not add redundant ARIA to native elements.

## Product constraints from the PRD (MVP)

- English-only UI, dark mode only. Header: "Help" (README on GitHub, new tab) and "Logout".
- Conversation list sorted by `updated_at` desc; each row: title, static relative time, message-count badge;
  inline title edit (click → input, Enter saves, Escape cancels, empty/whitespace rejected, max 100 chars);
  delete with a confirmation dialog "Delete conversation '[title]'?", no undo.
- Chat: stack layout, all messages left-aligned. User messages: lighter background, prefix "User".
  AI messages: participant colour as left border and prefix "AI - [alias]". Deleted participant:
  "(Deleted Participant)" in gray (#808080). Absolute timestamps (e.g. "10:45 AM"), date separators
  between days (e.g. "Dec 15"). All messages loaded at once (no pagination).
- Sending: a participant dropdown next to "Send" is required for EVERY message, sorted by alias, never
  remembers the last choice; disabled with tooltip "Add at least 2 AI participants in Settings" when the
  user has fewer than two. Send is disabled on empty/whitespace input. Limit 10 000 chars; a counter
  "9000/10000" appears from 9000. Input and dropdown are locked while waiting; a spinner shows where the
  reply will appear. Auto-scroll to the bottom only if the user is already at the bottom.
- A new conversation is a draft in UI state; it is persisted only after the first successful exchange.
- Errors from OpenRouter: one dialog with a single OK button, message 1:1 from the API `details`;
  the input is NOT cleared. Fixed texts: "Received invalid response from OpenRouter. Please try again."
  and "Network error - check your connection."
- Onboarding: sign-up/login → OpenRouter key (masked input with show/hide, validated on save, hard block on
  failure) → at least two participants; resume from the first incomplete step on next login.
- Participant creation: alias (max 30, letters/digits/space/`-_.`, at least one alphanumeric), model from a
  dropdown fed by `GET /api/openrouter-models` (loading spinner), colour generated by the UI and sent as
  `#RRGGBB`. Email shown read-only in Settings.
- The UI must branch on HTTP status, not on the error label: `401` → login, `412` → settings (missing key).
